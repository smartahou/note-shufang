## v1.7：目录 + 真正的数据加密上锁

### 目录

- 根目录是固定的虚拟目录，不能删除；旧笔记与新建目录默认都在根目录。
- 用户创建的目录全部是根目录下的一层子目录，不做多层嵌套。
- 点击目录只显示该目录中的笔记；编辑器顶部可把当前笔记移动到任意目录。
- 删除目录不会删除笔记，目录内笔记会自动移回根目录；如果目录文件异常或中断导致 `folderId` 失效，启动时也会自动把这些笔记修复回根目录。
- 目录增删改与笔记移动继续通过 SSE 在多开页面间实时同步。

### 笔记上锁

- 普通笔记可设置独立密码；加锁后列表只显示“已加锁笔记”，真实标题和摘要不会明文保存。
- 服务端使用 **scrypt** 从密码派生 256-bit 密钥，并用 **AES-256-GCM** 加密标题、类型、正文与本地图片附件。密码本身不写入任何数据文件。
- 本地图片会打包进加密载荷；若没有被其他未加锁笔记共同引用，原 `uploads/` 明文文件会移除。已解锁的加密笔记新增图片时走内存上传并直接写入密文，不先落一个明文图片文件；临时解锁时图片通过带会话令牌的解密接口读取。
- 解锁令牌只保存在 Note 进程内存和当前页面内存中，默认 30 分钟滑动有效；刷新页面或重启 Note 后需要重新输入密码。
- “立即锁定”只结束当前解锁会话，磁盘上的笔记始终保持加密；“解除加密”才会恢复普通明文存储。
- 加锁时会跳过“加锁前明文”的自动备份，并清理 Note 自己管理的 `backups/`、`quarantine/`、事务前驱及残留 JSON 临时文件中同一 note id 的明文记录，避免应用层继续留有可直接读取的历史副本。
- 书房不会向已加锁笔记直接写入截图/摘录；需要先在 Note 中解除加密后再作为书房目标笔记。

> 密码无法找回。应用可以保证自己管理的数据文件采用加密格式，但普通文件系统无法保证已经写过磁盘的数据块被“物理安全擦除”。

## 历史数据为什么不会因为融合而丢失

融合版**没有把用户数据搬进程序目录，也没有新建一套替代数据库**，而是继续沿用两个原程序的持久化路径。

### 笔记

继续使用原 v13 的持久化目录：

- Windows：`%LOCALAPPDATA%\Note`
- macOS：`~/Library/Application Support/Note`
- Linux：`~/.local/share/note`

核心数据仍然是：

- `data/notes.json`
- `uploads/`
- `backups/`

所以你以前 v13 已经写入上述目录的笔记，会被融合版直接读取。

### 书房

保持书房原有持久化逻辑：

- `~/.shufang/library.db`
- `~/.shufang/covers/`
- `~/.shufang/reader-cache/`

阅读进度、书目元数据、路径身份缓存仍使用原来的 `library.db`，不会因为程序换目录而重新生成一套数据。

## 重要升级原则

1. 不要删除 `%LOCALAPPDATA%\Note`（Windows）或对应平台的 Note 数据目录。
2. 不要删除用户主目录下的 `.shufang`。
3. 新版程序目录可以覆盖/替换；用户数据目录不要跟着删。
4. 为了最稳妥，首次使用融合版前，可以手工各复制一份上述两个数据目录作为冷备份。




## v1.3.1：富文本粘贴样式清理

- 截图时书房服务地址。

图片下方会显示来源条和 `打开原书 ↗`。在 Note 中点击后会跳回书房相同 SHA-256 的 PDF，并直接定位到对应页；框选截图还会在原页短暂标出当时的选区。

从笔记跳回原书时，首次定位**不会覆盖你原来的阅读进度**；只有随后主动翻页或滚动，书房才恢复正常的阅读进度记录。

### 关联为什么使用 SHA-256

书房原本就以文件 SHA-256 作为书籍身份。v1.3 延续这个规则，不用“文件名”或“绝对路径”做主关联。因此以后只改文件名、整理目录，只要 PDF 文件内容本身没有变化，重新扫描后关联仍可命中。

### 数据安全

书房**不会直接读写** `%LOCALAPPDATA%\Note\data\notes.json`。跨应用写入必须经过正在运行的 Note HTTP API，由 Note 自己执行上传、备份、事务写入与现有的数据清理规则。

如果 Note 没有启动，书房截图选择器会明确提示：

```bash
node note
```

不会退化成直接修改笔记数据库。

### 自定义端口

Note 默认 `3030`，书房默认 `39271`。如需修改 Note 端口，请让两个进程使用同一个 `NOTE_PORT` 环境变量；也可以给书房设置 `NOTE_ORIGIN` 指向实际 Note 地址。

## v1.2：彻底清理旧恢复脏数据，并关闭自动历史合并

这版针对已经被旧恢复机制污染的数据做一次主动清理。第一次启动 `node note` 时会：

- 从当前 `notes.json` 中删除标题以 `（恢复副本）` / `(恢复副本)` 结尾的旧恢复产物；
- 对重复 ID 只保留更新时间最新的一条；
- 对标题、类型、正文完全相同的记录只保留一条；
- 把旧 `backups/` 中的历史恢复快照全部移出活动目录，放入 `quarantine/cleanup-v1.2-*`；
- 把旧 `recovery-report.json` 一并隔离；
- 清理前的原始 `notes.json` 也会复制到 quarantine 中，仅作冷备份，程序永远不会自动读取它。

**从 v1.2 开始，启动时完全不会扫描 backups、旧工程目录或相邻 note 目录，也不会把任何历史快照自动合并回当前数据库。**

正常写入采用 `notes.json.previous` 作为一次事务保护：只有程序在“正在保存”的两个 rename 之间异常中断时，才允许把这个直接前驱文件恢复回来。它不是历史备份，不会产生合并、副本或复活删除数据的问题。

此外，每次启动都会做一次很窄的自检，只清理旧 bug 明确产生的 `恢复副本`、重复 ID 和完全重复记录；不会根据“相似正文”擅自删除正常笔记。

如果你以后想查看这次被清掉的原始内容，可以在 `%LOCALAPPDATA%\Note\quarantine` 中找到，但它不参与应用运行。

## 本次融合没有做什么

- 没有修改笔记的数据结构。
- v1.5 仅为书房 SQLite 新增 `reader_annotations` 划线表；原有书目、位置、阅读进度数据结构与内容不迁移。
- 没有把笔记和书房塞进同一个数据库。
- 没有修改已有阅读进度算法或书籍 SHA-256 身份逻辑。
- 笔记已取消自动历史合并，当前策略见上方 v1.2 说明。

v1.5 仍然不合库、不搬迁历史数据；跨应用内容继续只通过本地 HTTP API 写入 Note。书房新增的划线表与现有书目/阅读进度共用原 `library.db`，升级前自动备份。

更详细的原版说明在 `docs/` 目录。
